# Crawl admission and audit capacity

Documentation pages with repeated navigation must not queue the same target on every page. The crawler now atomically reserves a canonical target before queue admission. Root URLs, seeds, discovered links, resume records, and rendering-mode escalation use the normalized URL form used for stored page IDs, retaining the crawl's existing case-insensitive comparison. HTTP `.html`, `.htm`, and `.aspx` aliases share that form; query strings are retained and file URLs retain their extensions. The fetch entry keeps its requested URL, including its extension.

URL filtering and depth eligibility are evaluated before reservation so a rejected alias cannot suppress an eligible target. Existing scope/depth limits and GitHub repository delegation remain in force. Explicit blocked-response retries use their separate retry queue. Rendering-mode escalation deliberately releases the earlier canonical reservation and schedules another attempt. An entirely resumed crawl completes with no output.

The first eligible admitted route determines a page's expansion depth. There is no shortest-route guarantee when multiple eligible routes reach the same page at different depths. This change fixes rejection-before-admission behavior; it does not redesign traversal to revisit a page whenever a shorter route appears.

Repeated rejected discoveries now produce at most one audit event per exact normalized URL within a crawl. The event retains the first rejected occurrence's parent, depth, and reason; it is not a count of every repeated navigation edge. Duplicate pending targets no longer create `AlreadyVisited` audit events merely because several pages link to them. Depth skip details report the limit actually applied. The new `InScopeDepth` reason has numeric value 8; existing persisted reason values 0 through 7 are unchanged. Monitor options and inspection parsing derive their names from the enum.

The audit writer retains its bounded 10,000-entry buffer and synchronous fail-fast behavior. A full or stopping buffer throws `ScrapeAuditBufferException`; crawl workers cancel that crawl's work and propagate the failure to its output and caller. The message does not diagnose a database outage: a burst can exhaust capacity while persistence is merely delayed. The writer is shared, so other jobs may independently encounter capacity failures until the buffer drains.

This repair does not implement asynchronous producer backpressure or change the periodic flush loop. Unique crawl targets remain bounded by the source's discovered URL set, not by a new queue-size limit; `MaxPages` still limits fetches. Live corpus recovery uses the installed server until these changes are separately built and deployed.

Focused regressions cover repeated sidebar links and seeds, extension aliases, resumed targets, excluded and depth-rejected aliases, explicit retries, rendering escalation, repeated rejected targets, empty resumed crawls, and fail-fast audit propagation. The local browser fixture binds only to an operating-system-assigned loopback port; audit tests use substituted repositories and perform no model inference or external database writes.
