Issue 189: Ollama subject-classifier comparison and dependency updates
====================================================================

Recommendation
--------------
Retain Devstral Small 2 for now. It preserved the expected primary subject
identity in all 27 files. Ministral 3 8B was faster and used less graphics
memory, but misidentified the collection overview and repeated an extracted
model-name error. Gemma 4 12B lost a product identity and repeated that spelling
error in two files. No live classifier, embedding, or sorter setting changed.

Measured results
----------------

Gemma 4 12B             27/27            24/27            242.27 s     8.529 s      7,381,383,680

Each model made 27 requests: no validation retry was needed. All 81 document
results observed full model placement in graphics memory. Ollama reported no
resident models between model runs or after the final run. Reported allocation
is for the model, not total graphics-card use. The two candidate downloads used
the existing E:\Ollama Models store; no second Ollama installation was created.

These are one-pass batch measurements including any loading that occurred.
Keep-alive was zero, but requests can arrive before unloading completes. Do not
interpret the median as a guaranteed cold-start time. Ministral also had one
one-document smoke run before its batch; the other models did not. Operating
system caches, first-use work and unload scheduling can affect the comparison.
This experiment supports retaining Devstral for correctness, not a universal
speed ranking or a production qualification of every possible model setting.

Quality review
--------------
The score asks whether the primary label preserves the document's actual
product identity, or identifies a collection overview as an overview. It is
manual review of the 27 outputs, not a score for every word, numeric claim,
retrieval ranking, or answer generation. REVIEW-2026-10-22.csv contains every
primary label, identity verdict and exception note.

* Ministral labeled README.md, titled "Toshiba inverter manuals and motor
  datasheets", as a VF-S9 instruction manual. Its cited overview text contains
  an inventory table; it selected an item from the inventory as the main subject.
* Ministral and Gemma used TVF-AS3 for the VF-AS3 instruction PDF. The extracted
  heading contains that spelling, while filename and body preserve VF-AS3.
  Gemma also supplied VF-AS3 as an alias; the primary label still contains the
  extra letter. Gemma repeated TVF-AS3 on the VF-AS3 communication PDF as well.
* Gemma labeled the VF-S11 instruction PDF "TOSHIBA New Global Standard Inverter",
  omitting VF-S11 even though it is present in the filename and evidence.
* Ministral's VF-S11 instruction label preserves VF-S11 but incorrectly calls
  E6581158 a model number; it is the manual's document number. This is a separate
  wording defect, not an additional failed primary-identity score.
* Gemma added five secondary labels across three motor PDFs: induction-motor,
  connection-diagram and spare-parts subjects. The cited excerpts support them;
  they were not counted as invented subjects. Ministral and Devstral returned
  one subject per file. No unsupported broad alias was observed; Gemma's sole
  nonempty alias list supplied VF-AS3 in the case noted above.
* Devstral preserved all expected product identities, both Penske programming
  identities and the collection overview. Some of its first evidence selections
  are filenames or brief headings; this result does not certify description
  quality. All three passed the application's structural/evidence-key checks.

Before replacing Devstral, a follow-up should address overview-versus-inventory
selection, conflicting extracted headings versus named product identity, and
missing model designations. Candidate remedies are a general prompt clarification
and an evidence-based identity check that can request correction when filename,
title and selected label conflict. These have not been implemented or tested.
Keep their evaluation in issue 189 and use a broader held-out set before a switch.
No prompt was tuned to these results during this comparison.

The optional DirectML Phi-3 smoke passed but emitted native runtime warnings.
The repeated gpu_graph_id overwrite originates in GenAI 0.14.1 State::Run,
which adds the same configuration key during token generation. ONNX Runtime
1.24.4 warns whenever an existing key is added, even with the same value.
SaddleRAG does not set that key. A corrective native-package change would avoid
re-adding an unchanged value; it needs a compatible package and DirectML
qualification. No log suppression, runtime downgrade or graph-capture change
was applied. This follow-up remains in issue 189. Other native diagnostics
describe CPU placement of shape-related operations in that optional model;
they are separate from the GPU-only Ollama measurements above.
